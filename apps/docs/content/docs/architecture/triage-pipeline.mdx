---
title: Triage Pipeline
description: How Aziru sorts email threads from inbox to labelled category.
---

The triage pipeline is the core of Aziru. It runs inside the worker for every thread that needs sorting: both new threads arriving in real time and existing threads during a backfill. It reads the inbox through the provider seam (`packages/mail`), so the same pipeline serves Gmail and Outlook connections unchanged.

## Pipeline stages

```
Provider inbox (Gmail or Outlook)
    │
    ▼
1. Fetch thread
    │  Pull the full thread (all messages) through the mail provider.
    │  Only metadata and a short snippet are stored; full bodies
    │  are never persisted.
    ▼
2. Filter messages
    │  Select the most relevant messages from the thread to send
    │  to the AI (e.g. strip quoted replies, boilerplate footers).
    │  Keeps token usage bounded for long threads.
    ▼
3. Embed thread
    │  Produce a vector embedding of the thread summary using the
    │  configured embedding model (Gemini in production, Ollama locally).
    ▼
4. Sort (embedding similarity)
    │  Compare the thread embedding against embeddings of all taxonomy
    │  nodes. Candidate categories are scored by cosine similarity.
    ▼
5. LLM confirmation (optional)
    │  For ambiguous cases, a frontier LLM receives the thread summary
    │  and the top candidate categories and returns a final decision.
    │  The response is validated with Zod before it is used.
    ▼
6. Policy check
    │  Policy code validates the proposed destination:
    │  - The target category must exist in the workspace taxonomy.
    │  - Unknown node IDs and invalid paths are rejected.
    │  - Policy decides the final action, not the prompt.
    ▼
7. Apply label
    │  The provider applies the corresponding label to the thread.
    │  Aziru never modifies thread content or sends email.
    ▼
Done
```

Aziru can also generate a suggested draft reply for a thread. Drafts are always presented for user approval and are never auto-sent.

## Real-time vs. backfill

**Real-time:** The worker polls each connected inbox on a configurable interval (`INBOX_SYNC_INTERVAL_MS`, default 5 minutes), and enqueues new threads and threads with new messages for triage. When push is configured, near-real-time delivery replaces the wait between polls: Gmail via Google Cloud Pub/Sub, Outlook via Microsoft Graph change-notification subscriptions. Polling continues as a fallback for missed events.

**Backfill:** Users can trigger a full-inbox sort from the UI. This enqueues all threads in the inbox as individual jobs. Jobs are idempotent, so running triage on an already-sorted thread is safe and produces the same result.

## AI provider abstraction

The pipeline does not call the model API directly. It goes through the `packages/ai` provider abstraction, which routes to the configured backend:

| `AI_PROVIDER`  | Used for               |
|----------------|------------------------|
| `frontier`     | Production (Gemini by default; any OpenAI-compatible API) |
| `ollama`       | Local development      |
| `mock`         | Deterministic testing  |

Swapping providers requires only an env var change, no code changes.

## Taxonomy

Categories are defined in a per-workspace taxonomy: a tree of named nodes (for example `Work → Invoices`, `Personal → Travel`). Each node has a name and description used to generate its embedding, and the taxonomy is what the embedding sorter compares threads against. Aziru can also generate a starting taxonomy from your existing inbox.
